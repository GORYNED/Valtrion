# Changelog: Valtrion Core

Core (the `valtrion` Python package) and the Unity package `com.goryned.valtrion.unity` are versioned independently. The Unity changelog is in `integrations/unity/com.goryned.valtrion.unity/CHANGELOG.md`; `compat.json` lists compatible pairs.

## 0.8.8

- **The default number of Unity Editors at once is 2 on every platform.** It was 1 on macOS and 2 elsewhere. `host.json` `unityEditorSlots` still overrides it (for example `3` on a Windows host that can take three). A macOS host that needs the old limit sets `unityEditorSlots` to `1`.

- **`valtrion unity run` runs Unity in batch mode under Valtrion's leases and watchdog (#36).** `valtrion unity run [--project-dir DIR] [--unity PATH] [--lease-wait SEC] [--timeout-sec N] [--stall-sec N] [--purpose TEXT] [--host H --remote-project P] -- <Unity arguments>` replaces a project's own launcher around `Unity -batchmode` (EditMode tests, `-executeMethod`), the same on Windows, macOS and Linux. It finds the Editor of the project's `ProjectVersion.txt`, takes the `unity-project:` lease and then one `unity-editor` slot (renewed while it waits and while Unity runs, released in reverse order on every exit), adds the `host.json` `unityAccelerator` switches unless the arguments carry their own, and supervises Unity (hard timeout, stall of the `-logFile`, lost lease; the process tree is killed). The last stdout line is `STATUS <name>`; exit codes `PASS` 0, `FAIL` 1, `BLOCKED` 2, `STALL`/`TIMEOUT` 3. Unity exit 0 is `PASS`, 2 and 3 are `FAIL`, 1 is `BLOCKED` when the log names an open project or a license problem, else `FAIL`. `--host` forwards the call over the SSH transport without retries; the output arrives when the run ends. Nothing existing changes. See `docs/cli.md`.
- **`unity run` checks for Editors outside any lease and for free memory before it starts (#37).** With both leases held the run waits, within the `--lease-wait` budget, until no Unity Editor runs outside a lease (process list from `ps`, or PowerShell/CIM on Windows; an Editor below the holder of a live lease does not count) and enough memory is free (`vm_stat`, `/proc/meminfo`, CIM), else `BLOCKED` naming pids and numbers. New optional `host.json` setting `unityGuard`: `{"orphanEditors": true, "minFreeMemoryMiB": 2048}`; `false`/`0` turn the checks off. In `unity run` the checks are on without any setting. The pipeline's `build` stage (platforms that build in the Editor) and the Editor provider's launch make the same checks only when `host.json` has a `unityGuard` object (`{}` takes the defaults), after the leases are taken and within the job's lease wait (default 0, so `BLOCKED` at once with the reason); without the setting nothing changes for existing builds.
- **A united assembly list reaches Unity correctly.** `{assemblies}` of `valtrion select` is comma separated, but Unity's `-assemblyNames` reads `;`, so `editmode:A,B@runner` suites ran with the single name `A,B`. `unity run` now rewrites the value of `-assemblyNames` to the `;` form; `select` output is unchanged.
- **A run interrupted, and a lost connection, are defined (#38, partly).** Ctrl+C, SIGTERM, SIGHUP, SIGBREAK and, on Windows, console close/logoff/shutdown events stop Unity and release the leases (the handlers stay until the release is done). A command over SSH has no terminal and gets no SIGHUP, so `unity run --host` keeps a pipe open as the host command's input (`--stop-on-stdin-eof`, `SshTransport.lifeline`); the end of that input interrupts the run. A lost connection is `BLOCKED` with a note that the result is unknown, and a closed output no longer makes the host command fail with a traceback. Verified with real child processes on macOS only; whether a Windows host or every network failure delivers the end of input is not confirmed.
- **`unity run` fixes after review.** The pre-start check recognises an Editor by the program a process starts with, so a queued `valtrion unity run --unity .../Unity` or `sh -c` no longer counts as an orphan; a `-projectPath` argument wins over a broken `valtrion.json`; a license or lock text in a log left by an earlier run no longer turns a `FAIL` into `BLOCKED`; a lease lost after Unity had exited no longer replaces Unity's result; an interrupt right after a lease is created no longer leaks it.
## 0.8.7

- **`hosts sync` gives every SSH host one short `valtrion` command and no pile of versions.** With pipx on the host (as a module of the host's Python, next to it, or at the usual places) the wheel is installed with `pipx install --force`, and `valtrionCommand` is the short absolute pipx shim (`<home>/.local/bin/valtrion`) instead of a versioned path; pipx replaces its environment as a whole, so nothing is replaced unless the host is shown to be idle (jobs registry, leases, processes; otherwise `BLOCKED`, sync again later), and a failed version check after the install is reported as such. Without pipx the per-version virtual environment stays, now with a stable link `~/.valtrion/bin/valtrion` (`valtrion.cmd` on Windows) to the newest version, recorded as the command. Without pipx a sync removes `core/<X.Y.Z>` folders older than the installed version, never other names, newer versions, links, the stable link's target or the recorded command, and nothing at all while a job runs or a lease holder lives; with pipx only on `hosts sync --prune`. A host recorded with a versioned path is migrated by the next sync even at the current version. `hosts.json` `gdv.hosts/1` is unchanged. New: `valtrion doctor --host H` warns (`valtrionOnPath`) when `valtrion` is not found by plain name in a non-interactive SSH session, with the one-line fix; `valtrion hosts sync --ensure-path` adds the PATH line to `~/.zshenv` on a macOS host, only when asked. `hosts sync --json` rows have a `method` (`pipx` or `venv`).
- **Published-build retention is configurable.** New optional `host.json` setting `buildCache`: `{ "maxEntries": 20, "keepDays": 14, "dirtyKeepDays": 2 }` (all optional; the values shown are the defaults, so nothing changes without it). It sets the limits of the automatic cleanup after each publish, of `valtrion gc`, of the `disk.minFreeGiB` pressure cleanup and the default of `valtrion builds gc`; `--keep-days`, `--dirty-keep-days` and `--max-entries` still win. A build used in the last hour, an active job's build and the build just published are never removed. `perSource` (off by default; for example `1`) keeps only that many builds per source and platform: the build manifest now records the `source` (`checkout:<project>/<id>` for a managed checkout, else `dir:<project folder>`), and a new publication from the same source replaces the older ones (the manifest keeps the set of sources that published or reused a build, `sources`, and a build used by another source stays while it is among that source's newest); `builds gc --per-source N` does the same for one run. `publish` of a key that already exists now also updates the build `lastUsedUtc`. `maxEntries` is a non-negative integer, the day counts non-negative numbers; anything else, or an unknown key, is a `host.json` error. See `docs/work-root.md`.

## 0.8.6

- **A wired iOS device with an idle tunnel is attached (#22).** CoreDevice drops the tunnel of an idle device, and `devicectl list devices` then shows a wired, paired device as `available (paired)`; iOS discovery skipped it, so pipelines ended `BLOCKED: no attached device satisfies ...` with the device on the cable. Discovery now treats a wired, paired physical device as attachable and wakes its tunnel first with `devicectl device info lockState` (one bounded probe per idle device, then one more listing). Wireless devices whose tunnel is down are still not used. When no attached device fits, the reason says `device offline: <id> ...` for a registered device that would fit, or `no attached device satisfies: ... (no device with these settings is known on this host)`.
- **A refresh no longer erases what the owner set for a device (#23).** `devices --refresh` and `doctor --devices` keep a registered device that discovery did not find, marked `online: false` with its class, capabilities, alias and notes; it is online again (`lastSeen` updated) when it is found. `valtrion devices --forget DEVICE` (id or alias) removes one. `gdv.registry/1` gains the optional `online` and `lastSeen`; older registries stay valid. The host resolver does not count offline entries as attached devices.
- **A lost managed checkout is visible, and managed folders are marked (#24).** On the macOS host a disk cleanup removed a managed checkout; the next job recloned it and Unity imported `Library/` again, and `doctor` showed it as "not created yet". Now the build stage writes a `.valtrion-managed` marker into every managed checkout it prepares (excluded from git in `.git/info/exclude`, so `clean` keeps it and the tree stays clean) and records the use in `<valtrion home>/checkout-records/`. `doctor` reports a recorded checkout whose folder is gone as "was created, now missing (last used …)" with a warning (`checkouts.managed[].missing`, `lastUsed`; `marked` says whether the marker is there). `host.json` `projects.<name>.checkouts[].path` is optional: without it a checkout lives in `<valtrion home>/checkouts/<project>/<id>`, one place with the rest of the working state. Existing paths are unchanged; nothing is moved. `docs/work-root.md` says that the valtrion home and the managed checkouts are working state, not cache, and how to move a checkout safely.
- **Unity builds can use Unity Accelerator (#25).** New optional `host.json` setting `unityAccelerator` (`endpoint` `host:port`, optional `namespacePrefix`, `download` and `upload`, both default `true`). When it is set, the Unity batch command of the `ios`, `android`, `macos` and `windows` adapters gets `-EnableCacheServer -cacheServerEndpoint … -cacheServerNamespacePrefix … -cacheServerEnableDownload … -cacheServerEnableUpload …`; without it nothing changes. `doctor` reports the endpoint and whether it accepts a TCP connection (`unityAccelerator`). See `docs/work-root.md`.

## 0.8.5

- **A build can wait for free disk space (#14).** With `disk.minFreeGiB` set, `host.json` `disk.waitSec` (or `--disk-wait SEC` on `pipeline`, `build` and `run`) makes a `build` stage that still finds too little space after the cleanup wait, cleaning up and checking again every 30 s, instead of ending `BLOCKED` at once. The job waits before it takes the `unity-project:` lease and an Editor slot, so it never keeps them from the job whose end would free the space (no wait cycle). While it waits, `job.json` has `phase` `waiting-disk` (new value in `job.schema.json`) and a `log` event reports the free space and the minimum every poll; the wait does not count against `--timeout-sec`. `BLOCKED` (same reason: free space, minimum, largest consumers) when nothing appeared within the limit, or at once when the space would stay below the minimum even if every other active job ended. The default (0) keeps today's behavior.
- **A background job no longer fails when its staged CLI copy disappears (#18).** On the macOS host a pipeline job built and published correctly, then ended `FAIL` with `SchemaError: schema file not found: result.schema.json` because the staged copy of the CLI under `<workRoot>/tools` was removed while it ran and the runner read schemas and imported modules lazily. The runner now imports every module and reads every contract schema at start, and the staged copies live in `<valtrion home>/tools` instead of the work root (which is under `~/Library/Caches` on macOS). `valtrion.schema.Validator` instances of a directory share what was read.

## 0.8.4

Managed build checkouts: queued jobs of different commits no longer depend on a project folder that someone switched by hand.

- **Managed checkouts.** `host.json` `projects.<candidate.repo>` declares a small pool of checkouts (`id`, `path`, optional `remote`, `unityPath`, `default`). `--checkout ID|auto` on `pipeline`, `build` and `run` names one (with `--sha`; `--project-dir` and `--remote-project` are not used). Valtrion creates a missing checkout (clone of `remote`) and, when the `build` stage holds the checkout's `unity-project:` lease and an Editor slot, resets it to the job's commit: fetch if the commit is missing (an unknown commit is `BLOCKED` at once), forced detached checkout, `clean -fd` (ignored files such as `Library/` stay; the run's own folders are kept), `git lfs pull` when any tracked `.gitattributes` uses LFS, `HEAD` verified, tree read again. The dirty flag, Unity version and build-cache key are the commit's own.
- **Incremental builds (iOS).** A managed checkout keeps its build state: a persistent export folder (Unity exports with Append; the project's export method gets `-gdv-export-append 1`), persistent Xcode DerivedData and the IL2CPP cache in `Library/`, so a build after a small change recompiles only what changed. The state is used only under the checkout's lease and starts clean when the toolchain, build profile or signing changed, after a build killed half way, or with `valtrion build --clean` / `args.clean`. The built app is copied out before it is published. The folders are listed by `doctor` (`storage.incremental`) and released by the disk cleanup when nobody builds in them.
- **Preflight at submit.** Plans, pre-launch files, a missing project, and (managed) a commit that is not on the remote are found before the job is queued: `BLOCKED` at once, no lease taken.
- **Unmanaged folders** are never switched. With `--sha` they are checked at submit as before and again when the build starts: if another job moved the folder, the stage is `BLOCKED` naming both commits and nothing is built. For the Editor platform `HEAD` is verified again before each `run` stage.
- **Build output.** Stray `Builds/*` in a managed checkout is removed at each checkout (under the lease). The build output of a job stays in its work folder and goes away with the job.
- **Report.** `result.json` has an optional `checkout` object (project folder, commit, `id`, `switched`/`previousSha`, `created`, `fetched`); an event `log` with `data.checkout` says the same. `valtrion doctor` lists managed checkouts (commit, size, lease holder) and project folders outside them that hold a `unity-project:` lease.
- `compare.run_git` takes an optional timeout (the long git steps of a checkout use 30 minutes instead of 60 seconds).

## 0.8.3

Follow-ups of the host-disk cleanup (0.8.2).

- A job protects every published build it depends on, not only the last: `build-key.json` in its run folder lists all keys (a pipeline with an install by key and then a build uses two). A file written by 0.8.2 is still read.
- The cleanup finds the active jobs once per run instead of reading the whole job index several times, and `valtrion gc` now removes job index entries (`<home>/jobs/<jobId>.json`) whose run folder is gone, so the index no longer grows for ever.
- With several `build` stages, the leftovers of an unpublished earlier build are released when a later build is published (they were already; now covered by a test and by the flag that no longer resets).

- **Leftovers of a cancelled job no longer block the next build.** When `valtrion job cancel` closes a job whose runner is already gone (killed, crashed), the temporary paths it registered (an iOS export folder such as `Builds/iOS` inside the project, the build output) are removed with the rules of the runner's own cleanup (only under the run folder, the temp folders, the work root and the project; nothing protected or retained), with a `log` event. Before a `build` (the project lease held), jobs on the same project folder that were cancelled earlier and still list paths (cancelled by a version without this fix) are cleaned the same way, so a leftover export no longer ends the next build `BLOCKED` ("exportPath … already exists").

## 0.8.2

Host disk: a build host no longer fills up silently while builds queue.

- **Cleanup before a build (opt-in).** With `disk.minFreeGiB` in `host.json`, a `build` stage that finds less free space on the work root's volume first removes abandoned job folders (idle for an hour; running, retained and protected ones are never touched), run folders older than `disk.keepDaysUnderPressure` (default 2 days; active, retained and `--protect`ed runs are kept) and published builds beyond the cache retention.
- A published build that a still-active job depends on (it built or reused it and waits for the device, or installs it by key) is never removed by this cleanup, nor by `valtrion builds gc` / `valtrion gc` (the job records its key in its run folder). Other builds are removed by retention; they can be rebuilt.
- **Fail fast.** If the volume is still below the minimum, the stage ends `BLOCKED` with the free space, the minimum and the largest consumers; no toolchain is started (instead of `No space left on device` inside xcodebuild).
- **Early release.** The build output (and the folders the build registered as temporary) is removed from the job's work folder as soon as the build is published, or, when it could not be published, when the last stage is done (a player may run from its artifact). This applies to every host. A reused build needs no space.
- The periodic `progress` event of a running pipeline job (every `tickSec`, 15 s; it was already there and refreshes `lastProgressUtc`) now carries `currentPhase` and `buildLogBytes` (the size of the build logs, which grows while Unity or xcodebuild work), so a watcher can tell a quiet build from a stuck one.
- `valtrion doctor --json` has `storage`: free bytes, the sizes of the work root, the run folders and the build cache, `minFreeGiB` and `belowMinimum`.

## 0.8.1

- Fix: the timeout of a pipeline job (`--timeout-sec`) no longer counts the time the job spends waiting for a lease. A long `--lease-wait` for the Editor slot or the device used to end the job with `TIMEOUT` before the run started; now a wait is bounded by `--lease-wait` alone and the timeout covers working time (the `progress` event adds `workingSec`).

## 0.8.0

Pipelines lease the device only while they use it, build while the device is busy, and reuse builds. Existing pipelines need no change.

- **Stage-scoped leases.** The `unity-project` lease and the Unity Editor slot are held for the `build` stage only and released right after it; the `device:<id>` lease is taken at the first `install`/`run` and released after the last `install`/`run`/`collect`. A job never holds the device while it waits for a build resource, nor a build resource while it waits for the device, so there is no wait cycle (see `docs/cli.md`). With one device and one Editor slot the next job builds while the previous one is on the device. New `release_one` next to `acquire_one` (and `JobContext.release`).
- A device that cannot be served at all is still `BLOCKED` before the build; with `--lease-wait 0` a device held by another job is too. With `--lease-wait N` the job builds first and waits for the device afterwards.
- **Fair lease waiting.** A waiter joins a FIFO line per resource (ticket files under `<leases>/queue/`) and only the head may take the lease, so the longest waiter wins instead of whoever polls first after a release. Tickets of dead waiters expire; a non-waiting caller does not overtake live waiters.
- `job.json` has an optional `phase` (`waiting-build`, `building`, `waiting-device`, `on-device`), mirrored by `progress` events with `data.phase`.
- **Published builds.** The artifact of a `build` stage is moved to `<home>/builds/<key>/` (outside the work folder that cleanup removes) and listed in `result.json` as `build` (path, sha256, size, candidate sha, dirty, profile, toolchain, key, reused) and in a `progress` event.
- **Build reuse.** A clean tree with the same commit, platform, profile (and its `profiles.json` entry) and toolchain (Unity version, Xcode version on iOS, the device an iOS build is signed for) is built once and reused. A dirty tree is never reused. `"args": {"reuse": false}` forces a build. `valtrion builds list|show|gc` and `valtrion gc` apply retention (14 days unused, dirty 2 days, 20 builds).
- **`valtrion build`** (build only, no device) is implemented, and `install` takes a published build by key: `stage.args.artifactKey` or `valtrion run --artifact-key KEY`.
- `gdv.result/1` gains optional `build`; `gdv.job/1` gains optional `phase`. `compat.json`: Unity package 0.7.x pairs with Core `>=0.7.0,<0.9`.
