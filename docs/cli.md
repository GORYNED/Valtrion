# Command line

This page lists every `valtrion` command with its options, explains how a command finds the Unity project, and gives the exit codes. `valtrion --help` and `valtrion <command> --help` print the same from the installed version; the code is the reference if they differ from this page.

`valtrion` is also available as `python -m valtrion`. `valtrion --version` prints `valtrion <version> (contract <n>)`.

## Exit codes

| Code | Meaning |
| --- | --- |
| 0 | `PASS` |
| 1 | `FAIL` (also a `REGRESSION` verdict, and invalid content in `validate`) |
| 2 | `BLOCKED` or `NEEDS_PERMISSION`: a prerequisite is missing, nothing was proven |
| 3 | `STALL` or `TIMEOUT` |

`valtrion exit-code <STATUS>` prints the code for a status.

## Project discovery

Ordinary `job start` command jobs do not use Unity project discovery. They accept
an explicit `--cwd` and a grouping label `--project`; that label does not locate a
Unity project. See the [Core Quick Start](quick-start.md). `select`, `check-config`
and schema validation also work without Unity with explicit input files. `report`
requires app result files and does not turn command job status into app evidence.

Commands that need the Unity project (`run`, `pipeline`, `doctor --project`) resolve it in this order, first match wins:

1. `--project-dir <folder>`
2. the `GDV_UNITY_PROJECT` environment variable
3. the nearest `valtrion.json`, found by walking up from the current directory. Its content is `{"unityProject": "<path relative to the file>"}`.

`valtrion.json` may also hold `"checks": "<path relative to the file>"`, the check map that `select`, `report` and `check-config` use when `--checks` is not given. That lookup starts at the current directory, ignores `--project-dir` and `GDV_UNITY_PROJECT`, and ignores a file outside the repository. Without the key the map is `validation/device/checks.json` under the repository root; `--checks` always wins; an invalid `checks` value is `BLOCKED`. Build profiles are always read from `validation/device/profiles.json` inside the Unity project folder resolved by the three rules above.

`valtrion.json` only names a folder. It does not run anything. A missing folder or an invalid file is `BLOCKED`.

## Remote options

Many commands take `--host HOST` (run on a host from `valtrion hosts`) and `--remote-project DIR` (the working directory on an SSH host; or set `GDV_REMOTE_PROJECT`). The command that runs on an SSH host is the absolute path recorded by `valtrion hosts sync`; if none is recorded the command is `BLOCKED` and tells you to sync.

A remote project path is a path on the host. A POSIX path that starts with `/` and is typed in Git Bash, MSYS2 or Cygwin on Windows is turned into a Windows path before the program starts (`/Users/me/x` arrives as `C:/Program Files/Git/Users/me/x`). For a host that is not Windows, `valtrion` treats any drive path as such a rewrite; for a Windows host only a path below `X:/Program Files/Git/` (also `Program Files (x86)`), `X:/msys*/` or `X:/cygwin*/` whose next folder is a POSIX top-level one (`usr`, `Users`, `home`, `opt`, `tmp`, `mnt`, `Volumes`, `etc`, `var`, `private`) is suspect. A folder that is merely called `Git` or `msys64` (`C:\Git\Game`) is an ordinary path. It reports `the remote path ... looks rewritten by the local shell (MSYS path conversion); set GDV_REMOTE_PROJECT or use a script` as `BLOCKED` instead of probing the host and calling it unreachable; for a Windows host the message is only a warning on stderr (once per process), and the path is used. `hosts add --projects-root` is checked the same way. The same check applies to a value taken from `GDV_REMOTE_PROJECT`. A script that passes the path to `valtrion` (for example from Python) is not subject to the conversion.

## Hosts and diagnostics

| Command | What it does |
| --- | --- |
| `hosts [--json]` / `hosts list` | List the configured hosts. This machine is always listed. |
| `hosts add --id ID --ssh USER@HOST --os {windows,macos,linux} --artifacts-root PATH [--projects-root PATH] [--connect-timeout SEC] [--python PATH]` | Add or replace an SSH host in `hosts.json`. `--projects-root` must be absolute on the host (`/...` or `~/...` on macOS and Linux, a drive or UNC path on Windows). `--python` is the absolute path of a Python 3.10+ on the host; `hosts sync` uses only that one. |
| `hosts sync [--only HOST]... [--ensure-path]` | Install this core version on every SSH host (or the named ones) and record one short absolute `valtrion` command in `hosts.json`: the pipx shim when the host has pipx, otherwise `~/.valtrion/bin/valtrion` pointing to the newest per-version virtual environment. Without pipx, older unused `core/<X.Y.Z>` folders are removed (with pipx only with `--prune`; see install.md). `--ensure-path` also adds the command's folder to the non-interactive PATH on a macOS host (`~/.zshenv`). Exit 2 if any host is not synced. See [install.md](install.md). |
| `doctor [--json] [--devices] [--project [DIR]] [--host HOST] [--remote-project DIR]` | Read-only probe: Unity editors and modules, Xcode and `devicectl`, `adb`, GUI session and signing identities on macOS, free disk, a local CI runner (reported only, never touched), work root state, warnings for locations in protected folders (and, on Windows, for a virtualized or too long work root: see [work-root.md](work-root.md)). `--devices` also runs live device discovery. |
| `devices [--refresh \| --forget DEVICE] [--json] [--host HOST] [--remote-project DIR]` | Show the device registry, or refresh it by discovery through the providers. A registered device that a refresh does not find stays registered as offline (`online: false`, `lastSeen`) with its class, capabilities, alias and notes; it is online again when it is found. `--forget DEVICE` (id or alias) removes a device and its settings. |

**`doctor --project [DIR]`** also checks that the Unity package of the project (`com.goryned.valtrion.unity`, read from `Packages/packages-lock.json`) is supported by this core, using `compat.json`. Without `DIR` the project is resolved as described above. Result: `ok`, `skipped` (the project does not use the package or no project is given), or `BLOCKED` with the reason and the action to take (exit 2). A project whose package version cannot be read yet (a git package before Unity unpacked it) is `BLOCKED` with "open the project in Unity".

**`doctor --host H`** runs `doctor --json` on the SSH host and compares its core version with this one. A different version is `BLOCKED`; run `valtrion hosts sync`. It also runs `valtrion --version` by plain name in a non-interactive SSH session; when the host does not find it (or finds another version) the report has `valtrionOnPath` with `status` `warning`, and a warning with the one-line fix is printed. This does not change the exit code.

### How a host is judged reachable

A call to an SSH host ends in one of four readings, and only the last one says "unreachable":

| Reading | When | Reported as |
| --- | --- | --- |
| reachable | the remote command ran, whatever its own exit code (a failing command is not a failing host) | the command's own result |
| transient | ssh exited 255 (connection reset, banner or connect timeout, `MaxStartups` refusal, DNS or VPN flap, broken connection-sharing socket) or the call timed out | retried, see below |
| reachable but tool missing | the host answered and the shell reports exit 126/127 or "command not found" | `reachable, but the valtrion command is missing on the host`; run `valtrion hosts sync` |
| unreachable | a transient failure that persisted through every retry, or ssh refused for a reason no retry fixes (authentication denied, host key mismatch, bad ssh option, no matching algorithm) | `unreachable (<last error>)`, with the number of attempts when it was retried |

Calls that are safe to repeat (probing, `doctor`, `hosts sync`, `job tail`/`watch`, collecting artifacts) are tried up to 5 times, pausing 1, 2, 4 and 8 s between tries (15 s of pauses). No new try starts once 240 s have passed since the first, so one call takes at most 240 s plus the deadline of one more call (its timeout plus the connect timeout). A refusal that a retry cannot fix (for example `Permission denied`) is not retried. When the error names a broken control socket, the retry runs without connection sharing. Commands that are not safe to repeat (starting a run) are tried once.

Output around the answer does not matter: a login banner, a message of the day or profile output before or after the JSON of `doctor --json`, the `valtrion --version` line or the Python probe lines is skipped. Only a successful probe is cached (for 300 s); a failure is never cached. On a host reached without a login shell, `doctor` also looks for `adb` in the usual package folders (`/opt/homebrew/bin`, `/usr/local/bin` on macOS; `/usr/local/bin`, `/usr/local/sbin`, `/snap/bin` on Linux) after PATH, because that session's PATH does not include them.

| Command | What it does |
| --- | --- |

| `pipeline FILE [options]` | Run a `gdv.pipeline/1` as a detached job on a host chosen by capability. |
| `build --repo REPO --platform P [--profile NAME] [--sha SHA] [--no-reuse] [options]` | Build-only pipeline (one `build` stage, no device): builds on a host chosen by capability, or reuses a cached clean build, and publishes the artifact. Takes the options of `pipeline`. See [Build-only and install by key](#build-only-and-install-by-key). |
| `builds list/show KEY/gc` | The published builds of this host: list them, show one, or remove builds unused for a while (`gc [--keep-days 14] [--dirty-keep-days 2] [--max-entries 20] [--dry-run] [--protect KEY]`). `valtrion gc` also applies the default retention. |
| `job start/status/tail/watch/cancel` | Start a command as a detached, supervised job and inspect it. |
| `lease acquire/renew/release/status/list/name` | Leases on exclusive resources; `name` prints a lease name. |
| `unity run [options] -- UNITY_ARGS` | Run Unity in batch mode (EditMode tests, `-executeMethod`) under the host's leases and the watchdog, the same on Windows, macOS and Linux. See [`unity run`](#unity-run). |
| `collect JOB_ID --host HOST [--remote-project DIR]` | Pull a remote job's artifacts into the local artifacts root with the same layout. |
| `gc [--keep-days N] [--dry-run] [--protect PATH]` | Remove run folders older than `--keep-days` (default `retention.keepDays` of `host.json`, 30). Active, retained and protected runs are kept. |
| `retain JOB_ID` | Keep a run from `gc`. |
| `workroot show/checkout/inbox/release/sweep` | The work root, see [work-root.md](work-root.md). `inbox` creates `<workRoot>/jobs/inbox-<id>` and prints `{"inbox": "<path>"}`; a caller uses it to send files (see below). `show` and `sweep` also warn about unowned entries of the work root (never removed). |
| `workroot scratch create/release/list`, `workroot adopt PATH --yes` | Temporary copies for an agent under `<workRoot>/scratch/<id>`, with a marker and an expiry: `scratch create --name N [--project P --sha SHA (--source URL \| --repo PATH)] [--ttl-hours H] [--job-id J] [--lease R]` prints `{"scratch", "id", "expiresUtc", "release"}` (and `checkout` with `--sha`); `scratch release ID [--any-owner] [--dry-run]` removes exactly that folder when it is idle and yours; `adopt` makes an unowned folder of the work root a scratch folder (a git repository with unsaved work only with `--discard-unsaved-work`). See [Scratch copies](work-root.md#scratch-copies). |

**`run` and `pipeline` on an SSH host.** The command line is forwarded to the host. The plan, the pipeline and the pre-launch files are sent, and the project is found there; every other path on the command line (`--artifact FILE`, `--protect PATH`, `--project-dir` on a host without `projectsRoot`) is a path on the host, as given:

- *The plan is sent.* The caller reads the plan (for `pipeline`: the file and every plan and `prelaunchFiles[].local` file its stages name, resolved against the pipeline file's folder; for `run`: the plan and the `--prelaunch-file LOCAL` files, resolved against the plan's folder) and copies them with `scp` into a new private folder `inbox-<id>` that the host creates under its own work root (`valtrion workroot inbox`). The forwarded command names the copies (`<inbox>/1-<name>`, ...); the copy of a pipeline names its plans by their copies. A file that does not exist on the caller is `BLOCKED` before anything is sent. The plan's SHA-256 in the result is that of the bytes the host read, which are the bytes of the original. The job is started with the name of its inbox: the inbox is removed when the job's work directories are cleaned up, and `gc` and `workroot sweep` (both manual) keep the inbox of an active job and remove other inboxes that nothing has touched for hours.
- *The project is found on the host.* An explicit `--remote-project` (or `GDV_REMOTE_PROJECT`) is used as before: it is the working directory on the host, and the command line is forwarded unchanged. Otherwise, if the host has a `projectsRoot` (`hosts add --projects-root`), the project is `<projectsRoot>/<name>`, where `<name>` is the last folder of the Unity project this machine resolved (`--project-dir`, else `GDV_UNITY_PROJECT`, else `valtrion.json`) with the last segment of `candidate.repo` (`owner/Game`, `https://host/owner/Game.git` and `Game` all give `Game`) as the second name to try. A `~/...` projectsRoot on a macOS or Linux host is expanded by the host. The lookup happens only when the run needs a project (a project was resolved on this machine, the platform is `editor`, or the pipeline has a `build` stage); a run of an installed build on a device needs none and is not held back. The folder is checked on the host (`test -d`; on a Windows host with the Python recorded for it, and without one nothing can be asked, so the first name is used unverified, even when a second name exists, and the host checks the folder when the command starts and the run is `BLOCKED` there with `the Unity project folder ... does not exist on host`). If no name is a folder the run is `BLOCKED` with a reason that names the host, the `projectsRoot` and every name, its source and path that was looked for; a check that itself fails (ssh error, wrong Python path) is `BLOCKED` with the error, not reported as a missing folder. `--project-dir` of this machine is replaced by the path found, never forwarded. A host with neither gets the command line as given, including `--project-dir`.
- *The result says what was tested.* A result of a run on an SSH host records the project folder it used as `host.tools.projectDir`. `host.tools` is a free map of strings in `gdv.result/1` and in the Unity package's reader, so no schema changes; it is not a gap and is not listed under `unverified`.
**`run` options:** `--repo`, `--sha` (full 40-hex commit), `--app` (application id to launch on the device; for the `editor` platform the test assembly that holds the plan test, or `editor` to take `planAssembly` from the profile), `--profile`, `--device-class`, `--device-id`, `--platform` / `--target {ios,android,windows,macos,editor}`, `--artifact FILE` (install this build artifact before the run), `--artifact-key KEY` (install the published build with this key), `--build` (build the project first), `--launch-arg ARG` (repeatable), `--launch-timeout SEC` (how long the launch may wait for a slow start; 1 to 300, default `launchTimeoutSec` of `host.json`, else 60; see [providers](providers.md#android)), `--prelaunch-file LOCAL=REMOTE` (repeatable; push a file into the app's data folder before it starts), `--project-dir`, `--stall-sec`, `--timeout-sec`, `--lease-wait SEC`, `--protect PATH` (repeatable; cleanup never removes it), `--domain {auto,user,gui}`, `--foreground` (debugging only; see "macOS launchd domain" below), `--watch`, `--host` (pin the host), `--remote-project`.

**`pipeline` options:** `--disk-wait SEC` (a `build` stage waits up to this long for free disk space when `disk.minFreeGiB` is set, instead of being `BLOCKED` at once; default `disk.waitSec` of `host.json`, 0; see [work-root.md](work-root.md)), `--sha` (names the commit explicitly: the `build` stage checks it out in the project folder when it starts, see [Managed checkouts and the commit at build time](#managed-checkouts-and-the-commit-at-build-time); a pipeline without a `build` stage needs it to be the checked-out commit already, otherwise `BLOCKED` before any stage), `--checkout ID`, `--project-dir`, `--stall-sec`, `--timeout-sec`, `--lease-wait`, `--protect`, `--domain`, `--foreground`, `--watch`, `--host`, `--remote-project`. If `candidate.sha` in the file is missing or all zeros, the run uses the commit of the checkout and records it in every result. `externalUi` in a `run` stage answers the plan's `external.ui` requests with a command (see [protocol.md](protocol.md#during-the-run)); `prelaunchFiles` in a `run` stage push files before launch; `local` is absolute or relative to the pipeline file, `remote` is a plain relative path (no `..`, no drive, no leading slash); a bad entry is `BLOCKED` before anything starts.

**Commit and `dirty` in a result.** Before any stage, a pipeline reads the full `HEAD` of the repository that holds `--project-dir` (the project may be a subfolder of the repository or a folder of a linked worktree) and `git status` limited to that project folder. `candidate.dirty` is true when a tracked file there is modified, staged, deleted or conflicted, or an untracked file there is not ignored; edits elsewhere in the repository do not count, and neither do untracked files below the folders the run keeps itself (the artifacts root and the work root, when they lie inside the project); a tracked file below such a folder still counts. Git runs without an inherited `GIT_DIR`, `GIT_WORK_TREE` or `GIT_INDEX_FILE` and without optional locks. If git cannot answer (not a repository, a lock, a timeout), `unverified` of every result, also one that ends before a run, names the reason; an unreadable commit leaves the all-zero sha, an unreadable tree state leaves `dirty` true, and both stop the result from becoming a baseline. A genuinely dirty tree lists its first changed paths there and is still refused by `baseline promote`. `baseline promote` is stricter than the result's flag on purpose: besides `candidate.dirty` it requires the whole repository at `--repo-root` to be clean now (any change or untracked file anywhere, no exclusions), because the baseline file it writes is committed from that tree.

**`job start`** takes the command after `--`. Options: `--kind {run,pipeline,build,install,collect}`, `--project`, `--sha`, `--label`, `--stall-sec`, `--timeout-sec` (required), `--progress-file` (repeatable), `--heartbeat FILE` (a `gdv.heartbeat/1` whose `seq` must advance), `--cpu-progress`, `--contract-exit-codes`, `--lease RESOURCE[=SLOTS]` (repeatable), `--lease-wait`, `--lease-ttl`, `--cwd`, `--domain`, `--foreground`, `--watch`, `--host`, `--remote-project`.

**`job status JOB_ID`**, **`job cancel JOB_ID`**: `--host`, `--remote-project`. **`job tail` / `job watch JOB_ID`**: `--host`, `--remote-project`, `--from OFFSET` (byte offset in `events.jsonl`), `--stall-sec`, `--poll-sec`, `--unreachable-sec`, `--no-collect`. A watcher ends on the job's result and prints `GDV-RESULT <status> job=<id> offset=<n>`; if the host is unreachable for `--unreachable-sec` it reports `BLOCKED` with the offset to resume from while the job keeps running.

**`lease acquire RESOURCE`**: `--session`, `--holder-pid` (the process that holds the lease, default the parent of the command; it must stay alive and renew), `--owner`, `--host`, `--remote-project`, `--slots N` (a counted resource `RESOURCE:slot1..N`), `--ttl`, `--wait SEC` (bounded wait, then `BLOCKED` naming the holder; while it waits, a line `lease waiting <N> s: <reason>` goes to stderr after the first failed attempt and then about every 30 s), `--purpose`, `--worktree`. For the resource `unity-editor`, omitting `--slots` makes it the counted resource with the host's total of Unity slots (2, or `unityEditorSlots` in `host.json`); an explicit `--slots N` is used as given. Either way the lease held is one slot, `unity-editor:slotN`, so `renew` and `release` must name the `lease.resource` that `acquire` printed, not the bare `unity-editor`. Any other resource without `--slots` is a plain lease. `renew` and `release` take `--session`, `--holder-pid`, `--owner`, `--host`, `--remote-project`; `status RESOURCE` and `list` take `--host`, `--remote-project`. Environment: `GDV_OWNER`, `GDV_SESSION` provide defaults.

**`lease name unity-project PATH`** (also `--host`, `--remote-project`) takes nothing and writes nothing: it prints `{"resource": "unity-project:<hash>"}`, the lease name of the Unity project folder `PATH` (the same name the pipeline and the Editor provider use), so a launcher can pass it to `lease acquire` or `job start --lease` without computing the hash itself. The name is made from the resolved path, lower-cased on Windows and macOS; with `--host` it is computed on that host from the path as it is there.

**Lease events.** `job start --lease unity-editor` (no `=SLOTS`) takes a slot of the host's total, like `lease acquire unity-editor`; `--lease unity-editor=N` uses `N`. While a job waits for a lease (`--lease-wait`), it appends a `log` event to `events.jsonl` after the first failed attempt and then about every 30 s. Its `message` is `lease waiting <N> s: <reason>` and its `data` holds `resource`, `holder` (the reason, which names the holder) and `waitedSec`.

### `unity run`

```sh
valtrion unity run [--project-dir DIR] [--unity PATH] [--lease-wait SEC] [--timeout-sec N] [--stall-sec N] [--purpose TEXT] \
    [--[no-]lfs-materialize] [--host H --remote-project P] -- <Unity arguments>
```

Runs one Unity process in the foreground. It replaces a project's own launcher around `Unity -batchmode`: the leases, the watchdog, the process-tree kill and the status vocabulary are Valtrion's, and nothing in the command depends on the operating system.

- *Editor.* `--unity PATH` (an executable, or a macOS `.app`), else the Editor installed for the `m_EditorVersion` of the project's `ProjectSettings/ProjectVersion.txt`, found like the providers find it (Unity Hub folders of the OS, `GDV_UNITY_HUB_PATHS`, `GDV_UNITY_EDITORS`). No such Editor, or an Editor that cannot start, is `BLOCKED` with the reason.
- *Project.* `-projectPath` in the Unity arguments, else `--project-dir`, else `GDV_UNITY_PROJECT` / `valtrion.json` (as for the other commands; `--project-dir` is passed to Unity as `-projectPath`). Relative paths in the Unity arguments (`-projectPath .`, `-logFile Builds/x.log`) mean what they mean to Unity: relative to the working directory.
- *Leases.* First `unity-project:<hash>` (see `lease name`), then one slot of the host's `unity-editor` capacity (2, or `unityEditorSlots`). The holder is the `valtrion unity run` process itself; both leases (TTL 300 s) are renewed every 100 s while Unity runs (the project lease also while the run waits for a slot), and released in reverse order (slot, project) on every exit: a result, an error, Ctrl+C, SIGTERM/SIGBREAK/SIGHUP. The wait uses the fair queue of `lease acquire`, is shared by both leases and ends after `--lease-wait` seconds (default `leaseWaitSec` of `host.json`, else 1800) as `BLOCKED` naming the holder; it is never `TIMEOUT`. A lease that cannot be renewed while Unity runs (taken over or removed by hand) stops Unity (the whole process tree) and ends `BLOCKED`.
- *Git LFS preflight.* With the project lease held and before the Editor slot is taken, LFS pointer files in the project folder are turned into their content, so Unity never imports pointer text instead of an asset (a checkout or worktree made without the LFS smudge filter, as agents' worktrees often are). Nothing runs unless a tracked `.gitattributes` (or `info/attributes`) of the repository has `filter=lfs`: a project without LFS costs a few `git` calls and needs no git-lfs; a folder outside git is skipped. Otherwise the tracked files of the project folder with `filter=lfs` (`git check-attr`) of at most 1024 bytes whose text is an LFS pointer (`version https://git-lfs.github.com/spec/v1`, `oid sha256:…`, `size …`) are materialized. Each object is taken from the host's shared cache `<work root>/lfs-cache/objects/<aa>/<bb>/<oid>` (shared by every project, worktree and checkout of the host), else from the repository's own store, where git-lfs keeps it (`<lfs.storage>/objects`, a relative `lfs.storage` taken from the common git dir; by default `<git common dir>/lfs/objects/…`, the main checkout's store for a linked worktree), else fetched: one `git lfs fetch --include <the missing paths>` per batch, never for an object that is already on the host. When every object is cached, `git lfs` is not called at all and nothing goes over the network. Every object is copied into a temporary file while it is hashed, and renamed over the pointer only when its SHA-256 and size match the pointer; a damaged cache object is removed and the next source tried. Objects are linked (or copied) into the cache and the repository's store, so the next checkout and git-lfs's clean filter reuse them. The index entries of the materialized paths are then written again with the same blob (their stat data cleared, so git compares content instead of the pointer's size; an entry someone changed meanwhile, for example by `git add`, is left alone; assume-unchanged and skip-worktree flags are set again) and refreshed, also when the preflight is interrupted after the first file, and `git status` must show none of them. A path it shows that still holds exactly the placed object is put back to its pointer; a file someone edited meanwhile is never overwritten, it is reported as `lfs.changed-meanwhile`. Files below a parent folder that is a symbolic link or junction leading out of the working tree are not written (`lfs.path-outside-tree`). An interrupt (Ctrl+C, a signal, the end of the caller's input with `--host`) stops a running `git lfs fetch` within a fraction of a second; a git command that writes the index is never killed, it is left to finish first (an `index.lock` left by our own git that had to be killed on its timeout is removed; another git's lock is only reported, as `lfs.git-failed`). The time the preflight takes is added to the `--lease-wait` budget of the Editor slot, so a long download does not leave the slot wait without time. The run prints `lfs: N of M pointer file(s) materialized (...)` on stderr and, on stdout before the status, one line `LFS-PREFLIGHT {"code": …, "pointers": M, "materialized": N, "fromCache": …, "fromRepository": …, "fetched": …, "fetchCalls": …, "failed": [{"path": …, "code": …}], "reason": …}` (when pointers were found or the preflight failed). A failure is `BLOCKED` (exit 2) before Unity starts, the reason line begins `Git LFS preflight failed [<code>]` and names the files; nothing half-written is left, and a file that failed keeps its pointer. Codes: `lfs.git-lfs-missing` (git-lfs not installed, or no `filter.lfs.process`/`filter.lfs.clean` in the git config: run `git lfs install`), `lfs.auth-failed`, `lfs.network-failed`, `lfs.object-missing` (not on the remote), `lfs.fetch-failed` (another fetch error), `lfs.hash-mismatch`, `lfs.disk-space` (checked before anything is written, with a 64 MiB margin per volume), `lfs.write-failed`, `lfs.changed-meanwhile`, `lfs.status-dirty` (the clean filter does not give back the committed pointer), `lfs.path-outside-tree`, `lfs.unsupported-pointer` (a pointer with `ext-` extensions), `lfs.git-failed` (git failed in a folder that is inside a repository, for example `safe.directory`/dubious ownership, or a git older than 2.13; Unity is then not started on possibly unmaterialized files: fix git or turn the preflight off). A folder that is not inside any git repository is skipped. Turn it off with `host.json` `"lfs": {"materialize": false}` or for one run with `--no-lfs-materialize` (`--lfs-materialize` turns it on for one run when host.json turns it off). Known limits: only the project folder is scanned; `lfs.storage` is read from the git config only (not from `.lfsconfig`); attributes from `core.attributesFile` alone do not start the preflight.
- *Accelerator.* When `host.json` has `unityAccelerator`, its `-EnableCacheServer -cacheServerEndpoint …` switches are added, unless the Unity arguments carry their own `-EnableCacheServer` or `-cacheServer*`. Host settings stay in `host.json`.
- *Watchdog.* `--timeout-sec N` (default 0: none) is a hard limit; `--stall-sec N` (default 600, 0 = off) is `STALL` when the file named by `-logFile` has not grown for N seconds, and is off without a `-logFile` (or with `-logFile -`). Unity runs in its own process group (a Job Object on Windows); on timeout, stall and lost lease the whole tree is killed. Unity's console output is shown on stderr when it ends.
- *Status.* The last line on stdout is `STATUS <name>`, a reason line is printed before it. Exit codes: `PASS` 0, `FAIL` 1, `BLOCKED` 2, `STALL` 3, `TIMEOUT` 3. Unity exit code 0 is `PASS`; 2 (tests failed) and 3 (the run could not start, for example a compile error) are `FAIL`; 1 is `BLOCKED` when the last 256 KiB of the log (`-logFile`, else the console) contain `another unity instance is running with this project open`, `cannot open the same project`, `no valid unity editor license`, `unable to activate` or `license activation failed` / `error`, otherwise `FAIL`; any other code is `FAIL`. A `GDV-RESULT` line written to the console takes precedence as for other steps.
- *Remote.* `--host H --remote-project P` runs the same command on the SSH host through the command recorded by `hosts sync` (working directory `P`, so a relative `-projectPath .` is the project there), and returns its output and exit code. It is a plain foreground call, as `lease acquire --host`: the output arrives when the run has ended (no streaming), the call is not retried (a retried start could run Unity twice), and the SSH timeout is `--lease-wait` + `--timeout-sec` + 300 s (24 h when `--timeout-sec` is 0). The transport has no terminal, so a dropped connection sends no SIGHUP; the host learns of it from the end of the command's input instead (see "`--host`: the connection and the run" below). Use `job start --host` for a detached run that survives a drop. An unreachable host is `BLOCKED`.

- *Checks before Unity starts. On by default in `unity run`; the Editor provider's launch and the pipeline's build stage of an Editor-using platform make the same checks only on a host that opts in with a `unityGuard` object in `host.json` (`{}` takes the defaults below), with the job's `--lease-wait` (default `leaseWaitSec` of `host.json`, else 0: BLOCKED at once; the Editor provider's wait is also capped at 240 s); a lease lost during that wait ends it; a `unityGuard` setting that cannot be read only skips the checks with a note, it never blocks a build.* The checks are made **before** the Editor slot is taken: a run that waits for them holds only the `unity-project` lease and no slot, and keeps no place in the slot's waiting line, so the slots stay free for others meanwhile. The first run in line makes them every 5 s (one PowerShell/CIM query on Windows; a refusal is remembered for 5 s), each tool call is limited by the remaining wait. A run waits (within the same `--lease-wait` budget, a notice about every 30 s) until (1) no Unity Editor runs outside a lease and (2) enough memory is free; otherwise `BLOCKED` naming the pids and numbers. When both hold, the run takes a slot and makes the checks once more with the slot held; if something appeared meanwhile it gives the slot back and keeps waiting. An Editor is inside a lease when it or one of its ancestors is the holder process of a live lease, so Editors of other Valtrion runs (and their import workers) are never counted, while a crashed run's leftovers and an Editor started by hand are. Any Unity Editor executable counts (not only the Editors of the leased installations), recognised by the program a process starts with, never by its arguments: a queued `valtrion unity run --unity .../Unity` or `sh -c ".../Unity"` is not an Editor (on macOS and Linux the program is an absolute path whose later words do not start with `/`, `-` or a quote). The process list comes from `ps` (macOS, Linux) or PowerShell and CIM (`Win32_Process`, Windows), the free memory from `vm_stat` (free + inactive + speculative pages), `/proc/meminfo` (`MemAvailable`) or CIM (`FreePhysicalMemory`). What cannot be read is a note on stderr, never a block. `host.json` `unityGuard`: `{"orphanEditors": true, "minFreeMemoryMiB": 2048}` (defaults shown; `false` and `0` turn the checks off; other keys are an error).
- *Several test assemblies.* The value of `-assemblyNames` is rewritten to Unity's `;` separated form, so the united list that `select` puts into `{assemblies}` (comma separated, because `;` would end a shell command) can be passed as it is: `valtrion unity run -- ... -assemblyNames {assemblies}`. Other options, such as `-testFilter`, are passed unchanged.
- *When the run is interrupted.* Ctrl+C, SIGTERM, SIGHUP and SIGBREAK stop Unity's process tree and release the leases, and the result is `BLOCKED`. The handlers stay installed until the leases are given back, a further signal during that changes nothing, and the leases are released through the lease keeper (under its lock, so a renewal cannot recreate one). On Windows the console events that carry no Python signal (window or session closing, log off, shutdown) are handled the same way through `SetConsoleCtrlHandler`; this part could not be tested on a real Windows host. If the process is killed outright, the Job Object ends Unity (Windows) and the leases are freed once their TTL (300 s) has passed and the holder is gone (on POSIX the Unity process group is not ended by this).
- *Results that are still valid.* If a lease is lost after Unity has exited, Unity's own result is reported with a note; only a lease lost while Unity runs stops it (`BLOCKED`). The text of a `-logFile` counts for the `BLOCKED` classification only when the file was created or changed by this run (a log left by an earlier run is ignored). Stall detection needs a `-logFile` file; with `-logFile -` it is off.
- *`--host`: the connection and the run.* A command run over SSH has no terminal, so the host does not get SIGHUP when the connection ends. Instead the caller keeps a pipe open as the command's standard input (hidden option `--stop-on-stdin-eof`, added by `--host`): the caller writes a byte at once and then every 5 s, and when the host sees that input end after it has received at least one byte (the caller or its ssh died, the connection dropped), the run is interrupted like by Ctrl+C: Unity is killed and the leases are released. An input that never delivered a byte (closed, `/dev/null`, `NUL` behind a wrapper) ends at once and proves nothing, so the lifeline is then switched off with a note on stderr and the run goes on. A second signal, also one that arrives while the first is being handled or while the leases are released, changes nothing. On Windows the input watcher is not waited for at exit (a pipe cannot be polled there). This was verified with real child processes on macOS (a closed input and SIGTERM); it is not confirmed that an SSH server delivers the end of input promptly in every network failure (ServerAliveInterval is 15 s x 4 in the ssh options) or that a Windows host does. If it is not delivered, the run goes on until Unity ends or `--timeout-sec` expires, the leases are renewed meanwhile and released then, and the result is lost (the host ignores the closed output). The caller reports `BLOCKED` ("unreachable" or "did not answer") with a note that the result is unknown; it never reports PASS or FAIL for a run whose end it did not see. Check `valtrion lease list --host H` afterwards. A run that must survive the connection, or whose output must be followed, uses `job start --host`.

**macOS launchd domain.** A background job on macOS runs as a one-shot launchd agent. `--domain auto` tries the `user` domain and then `gui`; steps that sign need `--domain gui` (the login keychain). See [work-root.md](work-root.md). `--foreground` is for debugging only: it runs the job in the calling process (the terminal or SSH context), starts no launchd job and has no launchd domain, so it cannot sign over SSH (it can only where the calling terminal is itself in a logged-in GUI session) and `--domain` has no effect with it. `--foreground` together with `--domain user` or `--domain gui` is a usage error (exit 2). A signing step in a foreground job, or in any job outside the GUI session, ends `BLOCKED` with a message that names the context the job ran in; start the job without `--foreground`, with `--domain gui`.

## Comparison

| Command | What it does |
| --- | --- |
| `compare RESULT --plan PLAN --baselines FOLDER` | Compare a `gdv.result/1` with its baseline. Verdicts: `PASS`, `IMPROVED` (0), `REGRESSION` (1), `NOISY`, `NOT_COMPARABLE` (2). The output names the baseline file that was used. |
| `baseline promote RESULT --plan PLAN --baselines FOLDER --repo-root DIR [--main-branch NAME]` | Write a baseline under `<baselines>/<plan>/` from a passing, non-editor run of a commit on the main branch, made on a clean tree, with HEAD on that commit and a clean tree now. The file is `<deviceClass>.json`; a baseline of another OS major, build profile, Unity version or evidence for the same plan and device class is written next to it as `<deviceClass>-os<N>-<profile>-<digest>.json`. Promoting the same combination again replaces its file, also when the plan file changed. |

**Finding the baseline.** A baseline is found by content, not by file name: among all `*.json` files in `<baselines>/<plan>/` the one whose `planId`, comparability key and evidence equal those of the result is used (the newest `createdUtc` when several do). Plan ids or device classes that differ only in characters a file name cannot hold therefore never share or overwrite a baseline. If the plan has baselines but none with the key of the result, the verdict is `NOT_COMPARABLE` and the details name the key fields that differ in the closest one; with no baseline the details list the folders that were searched; a file that is not a valid `gdv.baseline/1` is named in the details. None of these is a `PASS`. A `budget` breach is still a `REGRESSION` without a baseline.

**Comparison in a pipeline.** With `compare` set in the pipeline, every run stage that passes is compared with the baseline of its own plan and key, whatever the other stages did. A relative `compare` folder is looked for under the pipeline file's folder and under `--project-dir` (both searched, never the working directory). The results of the stages are listed with their `comparison` in `summary.json`; `result.json` of the job is the first failing stage, otherwise the first stage with the worst verdict, and its comparison details name the other stages that are not `PASS` or `IMPROVED`. The job status is the worst comparison verdict of all stages that passed (`REGRESSION` is `FAIL`, `NOT_COMPARABLE` and `NOISY` are `BLOCKED`), unless a stage itself did not pass: then the job takes that stage's status and reason, and the reason also names the earlier stages whose comparison was a `REGRESSION` (their comparisons stay in `summary.json`). A baseline folder that holds a file which is not a valid `gdv.baseline/1` makes the comparison `NOT_COMPARABLE` (a `budget` breach stays `REGRESSION`) and the file is the first detail, because an unreadable file may be the newest baseline of the key; fix or remove it. If the pipeline and project folders hold different baselines for the key, the details say so. With `repeat`, the samples of the runs are joined without the warmup samples of every run after the first (a run with fewer samples than the warmup is left out and noted in `unverified`), so the comparison drops exactly one warmup per run; the `stats` of the joined metric describe the samples as joined, including the first run's warmup. Baselines promoted from `repeat` greater than 1 by earlier versions contain the warmup samples of the later runs; promote them again.

Two results are compared only when plan id, plan SHA-256, device class, OS major version, build profile and Unity version are all equal; otherwise `NOT_COMPARABLE`. A `budget` breach, or a median worse than the baseline by more than `regressionPct`, is `REGRESSION`; a baseline or run whose spread exceeds `regressionPct`, or too few samples, is `NOISY` (use a higher `repeat`); better by more than `regressionPct` is `IMPROVED`.

## Choosing checks for a change

A project describes in `validation/device/checks.json` (`gdv.checks/1`; see `examples/checks.json`) which paths belong to which kind of change and which checks each kind needs per level `L0` to `L4`.

| Command | What it does |
| --- | --- |
| `select (--base-ref REF \| --kind NAME) [--kind NAME ...] [--checks FILE] [--include-worktree] [--level L0..L4] [--json]` | List the checks the diff from the merge base with `REF` to `HEAD` needs, and/or the checks of the named kinds. Levels are cumulative; default `L4`. Exit 0, 1 (unclassified path under `"unclassified": "fail"`, invalid map or plan, unknown kind), 2 (git or file missing; neither `--base-ref` nor `--kind`). |
| `report (--base-ref REF \| --kind NAME) [--kind NAME ...] --results FOLDER [--checks FILE] [--include-worktree] [--level L0..L4] [--pr] [--json] [--sha SHA]` | Build the `Local verification` block: one row per selected check and platform with status, evidence and host. A check without a `gdv.result/1` file is `NOT_RUN`; a result for another revision does not count; a `PASS` with weaker evidence than the plan requires (a plan that declares none needs `physical`) or from a dirty tree is `NOT_VERIFIED`. `--pr` prints the block with its heading. `--sha` must equal `HEAD`. Exit code of the worst row; `NOT_RUN` and `NOT_VERIFIED` exit 2. |
| `result write KEY --status STATUS --out FOLDER [--reason TEXT] [--evidence KIND] [--platform P] [--repo-dir DIR] [--sha SHA] [--dirty] [--repo R] [--profile P] [--unity V] [--host-id H] [--started-utc T] [--finished-utc T] [--artifact KIND=FILE] [--count NAME=N] [--unverified TEXT]` | Write a `gdv.result/1` for a check the project ran with its own runner (L0, Editor suite, player), so `report` can show it. See below. |
| `check-config [--checks FILE] [--base-ref REF] [--include-worktree] [--warn-unclassified]` | Validate the check map, its areas and entries, every referenced plan (valid, unique `id`) and, with a base, the unclassified paths of the diff (an error, or a warning with the flag). |

**Results of checks Valtrion does not run (`result write`).** `report` matches a result to a check by `plan.id` equal to the check key. `valtrion result write KEY --status STATUS --out FOLDER` writes that document for `l0`, `l0:NAME`, `editmode:ASSEMBLY`, `playmode:ASSEMBLY` and `player:TARGET`; `KEY` is the entry exactly as `select --json` lists it (a suite of several assemblies is one key per assembly: write one result per assembly). The caller decides the status (`PASS`, `FAIL`, `BLOCKED`, `NEEDS_PERMISSION`, `STALL`, `TIMEOUT`): Valtrion does not read test XML or apply a skip policy. Any status but `PASS` needs `--reason`; `PASS` takes none. The commit is `HEAD` of the repository of `--repo-dir` (default: the current directory); `--sha` is accepted only when it equals `HEAD`. `candidate.dirty` comes from `git status` of that repository (untracked files under `--out` are not counted); `--dirty` marks it dirty even when git shows a clean tree, never the other way round, and `report` then shows `NOT_VERIFIED` instead of `PASS`. Defaults: `editmode`/`playmode` write `--evidence editor` and `--platform editor`; `l0` writes `host` evidence on platform `editor`; `player:ios|android|windows|macos` writes `host` evidence on that platform, and any other player target needs `--platform` (`editor`, `windows`, `macos`, `ios`, `android`). `--evidence` can be `editor` or `host` (an Editor suite only `editor`); `physical` and `emulator` are refused because the result names no device: a device or emulator run is recorded by `valtrion run` or `pipeline`. Only `l0`, `l0:NAME`, `editmode:`, `playmode:` and `player:` keys are accepted; a device plan id is refused. For `report` the newest result per platform and host counts and the worst of them is shown, so a FAIL written under another `--host-id` or `--platform` is not replaced by a later PASS under a different one; delete the old file. `--host-id` defaults to this machine's host id (transport `local`). `--artifact KIND=FILE` lists an existing file with its SHA-256 (such as the test XML); `--count NAME=N` records a number as a metric with unit `count`. Because no plan file exists, `plan.sha256` is the SHA-256 of the key's UTF-8 text. `runId` is deterministic from key, commit, host, platform, evidence and tree state, so the file name is too: writing the same result again replaces it, while a dirty result never replaces a clean one. The command prints the path of the file and exits 0 whatever the status written; 1 for refused inputs (nothing is written), 2 when git cannot be read. The document is validated with the `gdv.result/1` validator before it is written.

**Selecting by kind name (`--kind`).** `--kind NAME` (repeatable, or a comma list: `--kind scheduled --kind release,docs`) selects the checks of those kinds of the map directly, without a diff, at `--level` (cumulative, default `L4`). With `--base-ref` too, the named kinds are added to the kinds of the diff; `--include-worktree` only applies together with `--base-ref`. A kind that has no entries at the chosen level selects nothing (and `report` then has no rows for it), so pick the level that holds the checks you mean. A name that is not a kind of the map is exit 1 and the message lists the kinds. JSON output has `selectedKinds` (the kinds that were named, sorted) and `kindsNamedExplicitly`; `kinds` still lists every selected kind. Valtrion does not define a PR, scheduled or release mode and never runs anything on a schedule: a project names its own kinds in `checks.json` and chooses when to select them (for example from its own CI schedule).

**Named runners.** An optional top-level `runners` object of `gdv.checks/1` maps a name to a command template, so many entries and kinds can share one command: `"runners": {"unity-tests": "my-runner --assemblies \"{assemblies;}\""}` and `editmode:A,B@unity-tests`. The text after `@` is a name when it is exactly a key of `runners`; otherwise it is the literal command, as before (one ambiguity: a literal command that is exactly a runner name cannot be written; `check-config` warns when the map has `runners` and a bare name after `@` is not one of them). Suites that share one command merge into a single command with the united, sorted assembly list, in `select --json` as `editorCommands[]` (`runner` is the template, `runnerName` the name or null, `command` the expanded text). Placeholders: `{assemblies}` is the list joined with `,`; `{assemblies;}` is the same list joined with `;`, the separator of Unity's `-assemblyNames` and `-testFilter`. Expansion does no quoting, and a `;` ends a command in POSIX sh and PowerShell, so write the placeholder inside quotes in a template that is run through a shell: `-testFilter "{assemblies;}"`. `check-config` rejects any other `{assembl...}` look-alike (for example `{assemblies:;}`) in a `runners` template, naming the runner, and only warns about it in a literal command (text that was valid there before stays valid); it also rejects an invalid runner name (letters, digits, `.`, `_`, `-`; the schema cannot express a rule on property names, so this is a `check-config` rule) and warns when a runner name is also a program on PATH, because an entry that was that command now uses the runner.

**Excluding paths from an area.** An area may carry `"exclude": ["glob", ...]` (same glob syntax and rules as `glob`). A path belongs to the area when it matches `glob` and none of `exclude`; a path excluded from one area keeps the kinds of every other area it matches, and a path no area matches is unclassified as always. `check-config` rejects an exclude glob that is empty, absolute, contains `..` or a backslash.

**Cosmetic changes (`contentRules`).** An optional top-level `contentRules` array lets a map give a changed file whose whole diff is only comments and blank lines a cheaper kind. A rule has `glob` (same syntax as an area), `kind` (a kind of the map), `lineComment` (one or more markers such as `//`), and optionally `blockComment` `{"start", "end"}`, `reindent` (default false) and `codePrefixes`. It is opt-in per glob: without a rule nothing changes, a path no rule matches is never cosmetic, and when several rules match a path the first one in the array is used. Detection reads `git diff -U0` of the path (the file name is taken literally) and fails closed. A removed or added line is ignored when it is blank or a comment: after trimming it starts with a line marker, or it is a block comment that starts and ends on that one line with no other marker inside (`/* a */ f(); /* b */` is code); a line that starts with one of the rule's `codePrefixes` (for example `#!`, `#if`, `#pragma`, `//go:build`) is code although a marker starts it. Any other line is code and the path keeps its normal kinds, with one exception: with `"reindent": true` the code lines of each hunk may differ before and after only by spaces and tabs at their ends (re-indentation). Leave `reindent` off for languages and files where indentation or trailing whitespace is code (Python, YAML, Makefiles, shell line continuations, here-documents). Also code: a moved or reordered line, code turned into a comment, a trailing comment added to a code line, a change of whitespace inside a line (`"a b"` to `"ab"`), a line-ending change, a multi-line block comment, a binary file, a mode change or rename, an untracked file, a diff with bytes that are not UTF-8, and a line holding a separator that a language may treat as a line end (U+2028 and the like). When the whole diff of a path is cosmetic the path has the rule's kind only (also when no area matches it, so the `fail` policy does not see it); `select --json` lists `cosmeticPaths` (path to kind) and the text output a `COSMETIC` block. Known limits: text that looks like a comment inside a multi-line string literal (a C# verbatim string, a here-document) is read as a comment, so keep such files out of the rule's glob; markers that are also valid code in the file's language (`#` in C or shader files, `--[[` in Lua) need `codePrefixes` or another glob; one `git diff` runs per matching path. `check-config` rejects an unknown kind, a bad glob and an empty or space-padded marker, and does not apply content rules to its unclassified-path report.


**JSON files classified by their keys (`jsonRules`).** An optional top-level `jsonRules` array classifies a changed JSON file (a dependency manifest, a lock file) by which entries changed instead of giving the whole file the kind of its area: `{"glob": "libs/manifest.json", "root": "dependencies", "keys": [{"match": "libs.core*", "kinds": ["libs-core", "libs-ui"]}, {"match": "libs.ui*", "kind": "libs-ui"}, {"match": "*", "kind": "libs-other"}]}`. `glob` is as for an area; `root` is a top-level key of the file whose object holds the entries; each `match` is a pattern over entry names (`*`, `?` and `[...]` as in `fnmatch`, case-sensitive; `*` also matches `.` and `/`), and each entry gives its kinds as a list (`kinds`) or, as a short form, one `kind` (`check-config` rejects both together and neither). The file is read at the merge base and, with `--include-worktree`, in the working tree (a regular file; a symlink is not followed), otherwise at `HEAD`. Every added, removed or changed entry under `root` takes the kinds of the first `keys` entry whose `match` fits its name, so the order matters, and the path has the union of the kinds of all its changed entries, each kind once. A final `{"match": "*", ...}` is the explicit fallback kind for every other entry; without it an entry that fits nothing sends the whole file back to the kinds of its area. A value is compared as a whole: any change inside a nested entry changes the entry; `1`, `1.0`, `"1.0"` and `true` all differ; a number is compared by the text it was written with, so `1.0` against `1.00` counts as a change (fail closed) and two different numbers never collapse into one; key order does not count. The rule is opt-in per glob and fails closed to the kinds of the area map when: a changed entry fits no `match` and there is no `*` fallback; anything outside `root` changed (the fallback does not cover it); `root` is present but is not an object on either side (a missing `root` counts as empty); no entry changed (a reordered or reformatted file); the file is added or deleted or is replaced by a symlink; or it is not valid UTF-8 JSON (a BOM and either line ending are fine), has `NaN` or `Infinity`, or has duplicate keys at any depth; also when git cannot read a version. When several rules match a path the first in the array is used. A path judged this way is not unclassified (the `fail` and `widest` policies do not see it), and it takes no part in `contentRules`. `select --json` lists `jsonKeyKinds` (path to entry to list of kinds) and the text output a `JSON KEYS` block. `check-config` rejects an unknown kind (also inside a list), a bad glob and an empty `root` or `match`. Known limits: only one level of entries below a top-level key; entry names are matched as text, not as versions; a change that alters the meaning of the file without changing an entry under `root` is outside the rule, so keep such keys out of it (a change there makes the file fall back); one `git show` pair and a full parse per matching path.

Entries in a level list: `l0` or `l0:name`; `editmode:A,B[@runner]` and `playmode:A[@runner]` (Editor test assemblies; `runner` is a name from `runners` or the project's command, with `{assemblies}` / `{assemblies;}` replaced by the united, sorted list); `player:target`; `device:plans/name` (the file `plans/name.plan.json` next to `checks.json`). A path no area matches is unclassified: with `"unclassified": "widest"` every kind is selected, with `"fail"` `select` exits 1 and selects nothing. A result belongs to a check when its `plan.id` equals the check key.

## Leases by stage, build reuse

A pipeline job takes a resource only for the stage that needs it (automatic; there is no switch and no new field in existing pipelines):

| Stage | Holds | Released |
| --- | --- | --- |
| `build` | the `unity-project:` lease, then one `unity-editor` slot (this order, always) | right after the build, success or not |
| `install`, `run`, `collect` | the `device:<id>` lease, taken at the first `install`/`run` | after the last `install`/`run`/`collect` stage |

So with one device and one Editor slot the next job builds while the previous one is on the device, and the device is not leased during a build. `--lease-wait SEC` bounds each wait separately (the Editor slot for the build, then the device). The job's `--timeout-sec` does not count the time spent waiting for leases, only working time; the total wall time of a job is therefore bounded by `--timeout-sec` plus the sum of its lease waits (one `--lease-wait` per lease taken). While a job waits, `job.json` has `"phase": "waiting-disk"` (free disk space, see `--disk-wait`), `"waiting-build"` or `"waiting-device"`; while it works, `"building"` or `"on-device"`. The same changes are `progress` events with `data.phase` (`null` when cleared).

Why this cannot deadlock: a job never holds the device while it waits for the project or an Editor slot (the device is released before a later `build` stage), and never holds the project or a slot while it waits for the device (they are released in the build stage's `finally`, before the first device stage). A waiting job therefore holds no resource, and resources held by running work are released when that work ends, so there is no wait cycle. Inside the build stage the order project → slot is the same for every job. Waiting is fair: a caller that waits (`--lease-wait`, `lease acquire --wait`) puts a ticket in the resource's waiting line (`<leases>/queue/<resource>/*.ticket`, named by the time it started waiting, renewed at every poll) and only the first ticket may take the lease, so the longest waiter gets the resource and a later job cannot overtake it. A ticket whose process is dead and that was not renewed for a few polls (at least 5 s), or that was not renewed for 30 s or ten polls whatever its pid, is removed by the next waiter, so a crashed waiter does not block the line (the lease TTL does not matter for this). A caller that does not wait (`--lease-wait 0`) does not queue but does not overtake live waiters either (`BLOCKED`, naming the waiter in front). For a counted resource (`unity-editor`) the first ticket takes the next free slot.

A device that cannot be served at all (unknown id, wrong class, not attached) is `BLOCKED` before the build and without waiting, as before. With `--lease-wait 0` (the default) a device that another job holds is also `BLOCKED` before the build; with `--lease-wait N` the job builds first and waits up to `N` seconds for the device afterwards.

### Managed checkouts and the commit at build time

Jobs wait in the queue for a long time, and jobs of different commits cannot safely share a project folder that is switched by hand: switching it for the second job changes what the first, still queued job builds. Valtrion therefore owns the folders its builds run in.

**Managed checkouts.** `host.json` declares a small pool per project (see [work-root.md](work-root.md)); clients never create or switch these folders. Name one with `--checkout ID` (or `--checkout auto` for the project's default); the project is `candidate.repo`, and `--project-dir` and `--remote-project` are not used (an SSH host resolves the checkout from its own `host.json`). `--sha` (the full 40-character commit) is required:

```
valtrion pipeline FILE --host mac --sha SHA --checkout queue        # or: reference, auto
valtrion build --repo MyGame --platform ios --sha SHA --checkout queue --host mac
```

When the `build` stage starts and holds the checkout's `unity-project:` lease (then an Editor slot), valtrion makes the checkout be at the job's commit, whatever job used it before: a missing checkout is created (clone of the project's `remote`); a commit that is not there is fetched from `origin` (an unknown commit is `BLOCKED` at once, with the reason); the commit is checked out detached and forced, untracked files are removed (`clean -fd`; ignored files such as `Library/`, the import cache, stay; the folders the run itself keeps are never cleaned), `git lfs pull` runs when any tracked `.gitattributes` uses LFS, and stray build output in `Builds/*` is removed. `HEAD` is verified and the tree is read again (the result's dirty flag, the Unity version and the build-cache key are the commit's own). No other job can switch the checkout while the lease is held. A cancelled job stops between the git steps. A build that is reused from the cache still checks out first (the cache key needs the commit's profile settings).

**Any other folder** (`--project-dir`, unchanged) is never switched. With `--sha`, `HEAD` must be the job's commit when the job is submitted and again when its `build` stage starts: if another job moved the folder meanwhile, the stage ends `BLOCKED` naming both commits, and nothing is built. A pipeline without a `build` stage needs the commit to be checked out already (a managed checkout needs a `build` stage). For the Editor platform, whose player runs from the folder itself, `HEAD` is verified again before each `run` stage. Without `--sha` the pipeline builds what is checked out, as before.

**Incremental builds.** A managed checkout keeps its build state between jobs, so the second build after a small change takes minutes, not a full 15-30: Unity exports with Append into one persistent export folder, `xcodebuild` reuses one persistent DerivedData, and the IL2CPP cache in the checkout's `Library/` survives the reset (`clean` leaves ignored files). The folder is `<valtrion home>/incremental/<candidate.repo>/<checkout id>/` (`export/`, `DerivedData/`), outside the project and the job work folder, used only under the checkout's lease and not removed by job cleanup. The export method of the project is asked to append with the Unity switch `-gdv-export-append 1` (it adds `BuildOptions.AcceptExternalModificationsToPlayer`); without that support Unity re-exports in full, and Xcode still reuses DerivedData. The next build starts from nothing when the toolchain (Unity, Xcode), the build profile with its `validation/device/profiles.json` settings or the device the build is signed for changed, after a build that was killed half way (timeout, stall), or on request: `valtrion build --clean` or `args: {"clean": true}` on the `build` stage. The built `.app` is copied out of DerivedData before it is published. The size is in `valtrion doctor` (`storage.incremental`); under disk pressure the cleanup removes the folders of checkouts nobody is building in (the next build there starts clean). The note `incremental build: reused ...` / `clean build (...)` is in the result notes and the job events. Only the iOS platform keeps state this way today.

**Preflight at submit.** Before the job exists, so before it waits for any lease, valtrion checks what would end it `BLOCKED` anyway: the plans of the `run` stages and the pre-launch files, a `build` stage without a project, and for a managed checkout that the commit is on the remote (fetched into the checkout when it is missing; a checkout that does not exist yet needs a remote that answers). The result is an immediate `BLOCKED` with the reason; no lease is taken and nothing waits in a queue.

**Report.** `result.json` has `checkout` (the Unity project folder, the commit, the checkout `id`, whether it was reset from another commit with `previousSha`, `created`, `fetched`); an event `log` with `data.checkout` says the same, and the lease wait is in the job's lease events. `valtrion doctor` lists the managed checkouts (commit, size, who holds the lease) and the project folders outside them that hold a lease.

**Build output.** The build output of a job lives in its work folder and is removed when the job ends, whether it passed, failed, timed out or was cancelled (a cancelled job whose runner is gone is cleaned by `job cancel` and by the next build). A tool that must export inside the project (the iOS `exportPath`) is registered with the job and removed the same way; whatever is left in `Builds/*` of a managed checkout is removed at the next checkout, under the lease. Published builds follow the build-cache retention.

### Build-only and install by key

After a successful `build` stage the artifact is moved out of the job's work folder into `<home>/builds/<key>/` (a file artifact such as a Windows `.exe` takes its folder along, so `_Data` stays beside it; a folder artifact such as an `.app` moves alone; an artifact that is not inside the build output, like the Editor platform's project, is never moved and not published). It is reported in `result.json` as `build` (`key`, `path`, `kind`, `sha256`, `sizeBytes`, `candidateSha`, `dirty`, `profile`, `platform`, `toolchain`, `reused`, `builtByJob`) and as a `progress` event with `data.build`. The key of a clean tree is a hash of the project (`candidate.repo`), commit, platform, profile, the profile configuration in `validation/device/profiles.json`, the Unity version and the adapter's toolchain (iOS: the Xcode version, plus the device the build is signed for). A later build of the same clean key is not built again: the stage reports `reused from the build cache` and `build.reused` is true. A dirty or unreadable tree always builds and is published under a one-off key that no later build looks up. `"args": {"reuse": false}` on the `build` stage (or `valtrion build --no-reuse`) forces a build.

`valtrion build` runs a pipeline with a single `build` stage; the result is the build record. Its `plan.id` is the check key the build settles, `player:<platform>` by default or the value of `--check-key` (stage `args.checkKey`, must start with `player:`), so `valtrion report` matches it to the `player:TARGET` entry of `select`; `plan.sha256` is the hash of that text. Use `--check-key` when the target of the map differs from the platform (`player:win64`). Install it later without building: a stage `{"stage": "install", "args": {"artifactKey": "KEY"}}` or `valtrion run PLAN ... --artifact-key KEY`. Published builds are removed by `valtrion builds gc` (and after each publish, by `valtrion gc` and under disk pressure): unused for 14 days (dirty ones 2 days) or beyond the 20 most recently used, or the limits of `host.json` `buildCache` (`maxEntries`, `keepDays`, `dirtyKeepDays`, and `perSource` to keep only the newest build of each worktree or managed checkout and platform; `--max-entries`, `--keep-days`, `--dirty-keep-days` and `--per-source` of `builds gc` win); an entry used in the last hour is never removed (a job marks its build as used again just before it installs it). `build.path` of an old result can point to a build that `gc` has removed since; install by key reports that as `BLOCKED`. The reuse check compares the total size of the files with the recorded one, not their hashes. For an iOS build-only pipeline, `--device-id`/`--device-class` select the device the build is signed for (nothing is leased).

## Reserved commands

`install`, `launch`, `push`, `pull`, `screenshot` and `logs` are reserved for provider-level commands. They accept any arguments, print `not implemented`, and exit 2. Installs and launches currently happen through `run` and `pipeline` (installing a published build: `--artifact-key` / `artifactKey`); `build` is implemented, see above.
